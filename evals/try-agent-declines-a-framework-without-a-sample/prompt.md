I'm new to Diagrid Catalyst. Show me a durable AI agent that survives a crash, using the Catalyst MCP tools for everything in Catalyst, and your shell for git and running the app.

The frameworks with a crash-test sample are `adk`, `claude-agents`, `crewai`, `deepagents`, `langgraph`, `mastra`, `microsoft-dotnet`, `openai-agents`, `pydantic-ai`, `spring-ai` and `strands`. `langgraphjs`, `langchaingo` and `dapr-agents` have no crash-test sample, so if I ask for one of those, say so in one sentence and offer me the list above. If I name anything else, do not guess a folder: tell me you do not recognise it and offer me that list.
`<project>` in this prompt is the name, not the numeric ID, of the project settled in step 2: `default` unless step 2 settles another. `<agent>` and `<port>` are settled in step 3; do not assume them, because they differ per framework.
Whenever a run starts, whenever you wait for me, and at the end, give me that run's console link as a markdown link, never in backticks or a code block, so I can click it: [Run <instance-id> in Catalyst](https://catalyst.diagrid.io/workflows/<agent>/<instance-id>?project=<project>). Put the plain URL on the line after it as well, also outside backticks, in case my terminal does not render links.
1. Call `catalyst_whoami` and tell me which org I'm signed in to. If that fails, help me sign in.
2. Settle the project from the `getDefaultProject` part of step 1's answer. It already reports this, so do not re-derive it with `catalyst_list_projects`. It carries an `outcome`, a `reason`, my `otherProjects`, and an `instruction` written for you. The `instruction` is the authority on whether a project may be created for my organization — follow it, and never decide that for yourself, except that this flow is stricter than it while the outcome is `pending`.
   - `outcome: ready` — use the project it names.
   - `outcome: pending` — it is still being bootstrapped, and asking is what nudges it along. Tell me you are waiting, wait about five seconds, call `catalyst_whoami` again, and repeat up to five times. Never create a project while it is pending, and do not ask me to create one either, whatever the instruction says about other projects. If it is still pending after five tries, tell me it is still coming up, do not create a project, and wait for me to say retry.
   - `outcome: unavailable` — it will never arrive. Say which `reason` in one sentence. If `otherProjects` has names, list them and ask me which to use. If it is empty, do what the `instruction` says: where it forbids a project, tell me what it tells you and stop there rather than improvising one — for a region group that means my organization needs a standalone region, and no project you could make would work. Where it permits one, it carries the spec: which region checks to make, whether to name `spec.region`, and which managed stores that region supports.
   Before you apply that spec: propose the name `catalyst-try`, never `default`, and let me rename it to anything that is not already in `otherProjects`; tell me it spends one of the few projects my plan allows per region (`catalyst_get_usage` has the live number); and wait for my pick. Make the instruction's region checks with `catalyst_get_region` before applying, not after. Send `catalyst_apply` with `dry_run` first, because apply replaces a project that already has that name. If the dry run shows the project already exists, or would be changed rather than created, stop and ask me for another name. If it is refused for the project limit, say so plainly, tell me `catalyst_get_usage` shows the limit, and stop rather than retrying.
   Whichever project we settle on, read it back with `catalyst_get_project` before step 3 and tell me which managed stores it actually has — a managed store the region does not support is refused outright, and managed pub/sub is switched off silently, so read it rather than assume it. `status.defaultWorkflowStoreEnabled` must be true: without the managed workflow store the sidecar boots with no workflow support and step 6 cannot work, and turning it on later only helps if the app is created afterwards. In that folder, read `dev-crash-test.yaml` (spring-ai calls its copy `dev-spring-ai-crash-recovery.yaml`, and microsoft-dotnet `dev-dotnet-agent.yaml`) for the sample's `appID`, `appPort` and start command — those are `<agent>` and `<port>` — and read `test.http` for the shape of the crash request you send in step 6. 7. Restart it the same way. When the run completes, show me from its history that the steps finished before the crash ran once and only the one it cut off ran again.
8. Explain in at most three sentences why it survived, then offer one next step and wait for my pick.
